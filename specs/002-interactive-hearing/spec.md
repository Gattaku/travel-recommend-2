# Feature Specification: インタラクティブ・ヒアリング機能

**Feature Branch**: `002-interactive-hearing`
**Created**: 2026-03-23
**Status**: Draft
**Input**: ユーザーへのヒアリングを通じて家族の趣味・旅行の方向性・子供の好みなどを把握し、その情報をもとにより精度の高い旅行先提案を行うインタラクティブなヒアリング機能

### User Story 1 - ヒアリングを通じたパーソナライズ提案 (Priority: P1)

家族旅行を計画したい親が、既存の基本条件（時期・予算・スタイル・エリア）に加えて、
システムからの質問に答えることで旅行の方向性をより具体化できる。
質問は「家族の趣味・好み」「旅行で重視すること」「子供が喜ぶ体験」「移動手段の希望」
「食事のこだわり」などを段階的に聞き、回答内容を踏まえた精度の高い旅行先提案を受け取る。

**Why this priority**: 既存の固定条件だけでは「自然体験」が釣り堀なのかハイキングなのか
キャンプなのか判断できない。ヒアリングによる情報追加が提案精度を決定的に向上させる。

**Independent Test**: 基本条件を入力した後に「もっと詳しく教える」を選択し、
3-5問のヒアリングに回答して「提案する」を実行すると、
ヒアリング内容を反映した提案が表示されれば独立して価値を提供できる。

**Acceptance Scenarios**:

1. **Given** 基本条件（夏・国内・予算10万円・自然体験）を入力済みの状態で、
   **When** 「もっと詳しく教える」ボタンを押すと、
   **Then** 家族の趣味や旅行の方向性に関するヒアリング質問が表示される。
2. **Given** ヒアリング画面で「子供が虫好き」「川遊びがしたい」「車移動OK」と回答した状態で、
   **When** 「この条件で提案して」を実行すると、
   **Then** 回答内容を反映した提案（川遊びスポットや昆虫採集ができるキャンプ場など）が表示される。
3. **Given** ヒアリング画面が表示されている状態で、
   **When** 「スキップして基本条件だけで提案」を選択すると、
   **Then** 既存の基本条件のみで提案が生成される（既存フローと同じ動作）。
4. **Given** 基本条件のみで提案結果が表示されている状態で、
   **When** 「もっと絞り込む」ボタンを押すと、
   **Then** ヒアリング画面が表示され、追加情報を入力して再提案を受けられる。

### User Story 2 - ヒアリング内容の保存と再利用 (Priority: P2)

過去にヒアリングで回答した家族の好み情報（趣味・子供の好み・食事制限など）が
プロフィールとして保存され、次回以降の提案リクエスト時に自動で反映される。
ユーザーは保存されたプロフィールを確認・編集できる。

**Why this priority**: 毎回同じ質問に答えるのは煩わしい。一度回答した好み情報を
蓄積することで、使い込むほど提案精度が上がる体験を提供する。

**Independent Test**: ヒアリングに回答して提案を受けた後、新しいセッションで
基本条件を入力すると前回の好み情報が自動反映されていれば独立して価値を提供できる。

**Acceptance Scenarios**:

1. **Given** ヒアリングで好み情報（趣味：釣り、子供：虫好き）を回答して提案を受けた後、
   **When** 新しい提案リクエストを開始すると、
   **Then** 前回の好み情報がヒアリング画面にプリセットされている。
2. **Given** 保存済みの好みプロフィールがある状態で、
   **When** プロフィール画面で好み情報を編集すると、
   **Then** 変更が保存され、次回の提案に反映される。
3. **Given** 保存済みの好みプロフィールがある状態で、
   **When** 「今回だけ違う条件で探す」を選択すると、
   **Then** 一時的に保存済みプロフィールを無視してヒアリングを最初からやり直せる。

---

### User Story 3 - ヒアリング質問のカスタマイズ (Priority: P3)

家族構成や基本条件に応じて、ヒアリングで表示される質問が動的に変わる。
例えば、幼児がいる家族にはベビーカー対応やオムツ替えスペースに関する質問が追加され、
海外旅行を選んだ場合はパスポートやビザ、言語の不安に関する質問が表示される。

**Why this priority**: 画一的な質問では的外れな項目が出てしまう。
条件に合った質問を出すことでヒアリングの質が向上するが、P1・P2が先に完成している必要がある。

**Independent Test**: 幼児がいる家族構成と海外エリアを入力した場合に、
幼児・海外向け固有の質問が表示されれば独立して価値を提供できる。

**Acceptance Scenarios**:

1. **Given** 子供の年齢に「1歳」を含む家族構成で、
   **When** ヒアリング画面が表示されると、
   **Then** 「ベビーカー対応の施設が必要ですか？」「離乳食対応のレストランは重要ですか？」
   など幼児向けの質問が含まれる。
2. **Given** エリアを「海外」に設定した状態で、
   **When** ヒアリング画面が表示されると、
   **Then** 「英語圏と非英語圏どちらが希望ですか？」「フライト時間の上限は？」
   など海外旅行向けの質問が含まれる。
3. **Given** 大人のみ（子供なし）の家族構成で、
   **When** ヒアリング画面が表示されると、
   **Then** 子供向けの質問（子供の好み、ベビーカー等）は表示されない。

---

### Edge Cases

- ヒアリングの全質問をスキップした場合は、基本条件のみで提案する（既存フローと同等）。
- ヒアリング途中でブラウザを閉じた場合、回答済みの内容は一時保存され、再度アクセス時に続きから回答できる。
- ヒアリング内容が矛盾する場合（例: 予算1万円で海外リゾート希望）、提案生成時に矛盾を指摘して条件の見直しを提案する。
- 保存済みプロフィールの好み情報と今回のヒアリング回答が異なる場合、今回の回答を優先する。
- ヒアリング質問が0件になる構成（極端に単純な条件）でも、エラーにならず基本条件のみで提案される。

---

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは基本条件入力後に「もっと詳しく教える」オプションを提供しなければならない。
- **FR-002**: ヒアリングは「家族の趣味・興味」「旅行で重視すること」「子供が喜ぶ体験」「移動手段の希望」「食事のこだわり」のカテゴリで質問を表示しなければならない。
- **FR-003**: ヒアリングの各質問は選択肢（複数選択可）またはフリーテキストで回答できなければならない。
- **FR-004**: ユーザーはヒアリングの任意の質問をスキップできなければならない。
- **FR-005**: ヒアリング回答はAIへの提案リクエストのプロンプトに組み込まれ、提案精度を向上させなければならない。
- **FR-006**: 既存の「基本条件のみで提案」フローは変更せず維持しなければならない。
- **FR-007**: 提案結果表示後に「もっと絞り込む」からヒアリングを開始して再提案できなければならない。
- **FR-008**: ヒアリング回答から導出された好み情報をユーザープロフィールとして保存しなければならない。
- **FR-009**: 保存済みの好みプロフィールは次回の提案リクエスト時にプリセットされなければならない。
- **FR-010**: ユーザーは保存済みの好みプロフィールを確認・編集・削除できなければならない。
- **FR-011**: 家族構成（子供の年齢帯）や選択エリアに応じて、表示されるヒアリング質問が動的に変化しなければならない。
- **FR-012**: ヒアリング途中の回答は一時保存され、ブラウザ再アクセス時に復元されなければならない。

### Key Entities

- **HearingQuestion（ヒアリング質問）**: カテゴリ・質問文・回答形式（選択肢/フリーテキスト）・表示条件（家族構成やエリアに基づく）を持つ質問データ。
- **HearingAnswer（ヒアリング回答）**: ユーザーが各質問に対して選択・入力した回答。質問IDと紐づく。
- **HearingProfile（好みプロフィール）**: ヒアリング回答から導出・蓄積された家族の好み情報。次回以降の提案に自動反映される永続データ。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ヒアリング画面の全質問に回答してから提案が表示されるまで、40秒以内に完了する。
- **SC-002**: ヒアリング回答を含む提案結果に対して、ユーザーが「この提案は自分に合っている」と感じる割合が、基本条件のみの提案と比較して向上する（ユーザーフィードバック機能で計測）。
- **SC-003**: ヒアリング全体の所要時間が2分以内で完了できる（質問数は3-5問に収まる）。
- **SC-004**: 保存済みプロフィールがある場合、2回目以降の提案リクエストでヒアリング所要時間が初回の半分以下になる。
- **SC-005**: ヒアリングをスキップした場合、既存フローと同じ速度・品質で提案が生成される。

---

## Assumptions

- ヒアリング質問の初期セットは開発時に定義する。質問の追加・変更はコード変更で対応する（管理画面は初期スコープ外）。
- ヒアリング回答は Claude へのプロンプトに自然言語として組み込む。構造化されたフィルタリングではなく、AIの文脈理解に依存する。
- 好みプロフィールは既存の Supabase DB に保存する。
- ヒアリング途中の一時保存はブラウザのローカルストレージを使用する。
- 質問の動的生成（P3）における条件ロジックは、家族構成とエリアの2軸で分岐する。それ以上の複雑な条件分岐は初期スコープ外。
